THE THESIS

THE HUMAN IS NO LONGER THE BOTTLENECK.

Human 1.0 is the default operating model of the digital age: one mind, one screen, one queue. Every task waits for the person to open the app, hold the context, make the move and remember what comes next.

Human 2.0 changes the unit of work. The person remains accountable, but execution is distributed across a trusted agent network. Some agents live beside the operator on physical machines. Others live in the cloud. Each has a role, a place to run and a controlled path back to the human.

Yuval Noah Harari argues that what makes humans distinctive is not individual intelligence but the ability to cooperate flexibly through shared fictions — laws, money, institutions. The network is the operating system of civilization. The problem is that the individual human operator is still running on a legacy kernel: one foreground thread, one active context window, one queue.

Max Tegmark writes about a coming wave of AI systems that will not just answer questions but take actions in the world. The operative word is actions. A system that can act, persist, observe results and retry is not a tool you use. It is a process you supervise. That distinction is the entire story.

The upgrade is not replacing the human. It is increasing the number of useful, supervised processes one human can keep in motion.

PART I — THE TRANSITION

FROM HUMAN 1.0 TO HUMAN 2.0

A practical transition from app operator to agent-system operator.

BOTTOM LINE

The human operator is no longer the bottleneck — the operating model is. Human 1.0 runs one foreground thread. Human 2.0 runs a named, countable fleet of agents with explicit boundaries, parallel lanes and a supervisor who remains accountable. The lab described here is operational: four physical agents, two cloud agents, one human. The architecture is accessible now. The discipline is not.

01

THE LIMIT OF HUMAN 1.0

The first digital transformation gave people faster tools but left the operating model unchanged. Email replaced mail. Dashboards replaced binders. Cloud apps replaced desktop software. The human still became the integration layer: copying information, deciding what mattered, moving it between systems and carrying unfinished work in memory.

That model scales poorly. More software creates more interfaces. More data creates more checking. Every new capability competes for the same finite attention. Human 1.0 is powerful, but throughput remains tied to how many contexts one person can safely hold.

Yuval Noah Harari has argued that what makes humans distinctive is not raw computation but the ability to cooperate flexibly in large numbers through shared fictions — laws, money, institutions. The operating system of civilization is narrative. The problem is that the individual human operator is still running on a legacy kernel: one foreground thread, one active context window, one queue. The tools have accelerated. The coordination model has not.

02

THE AGENT SHIFT

An agent is more than a chat window. It is a unit of delegated execution with context, tools, a computing environment and a reporting path. Once agents have durable places to run, the architecture changes. The question is no longer "Which app should I open?" It becomes "Which agent should own this outcome, and what evidence should it return?"

This is the bridge to Human 2.0: intention stays centralized while execution becomes distributed. The human defines direction, reviews consequential choices and remains accountable. The network carries research, monitoring, production and routine follow-through.

Max Tegmark has written about the coming wave of AI systems that will not just answer questions but take actions in the world. The operative word is actions. A system that can act — that can persist, observe results and retry — is not a tool you use. It is a process you supervise. That distinction is the entire story.

03

WHY HYBRID WINS

Physical and cloud agents solve different problems. Local devices give the system a stable foothold near private networks, peripherals and long-running processes. Cloud computers give agents reach, availability and independence from any one room. The hybrid model uses both instead of forcing one environment to do everything.

In this lab, the physical plane is concrete: three LAN-connected mini PCs plus a custom PC running agent four. The cloud plane is equally explicit: Instinct and Muse each occupy an independent cloud computer. The iPhone and MacBook are access controllers, not agent hosts. That distinction matters because a system is easier to secure and operate when every node has a name, purpose and boundary.

The hybrid architecture is also an argument about trust. A pure cloud model makes every action remote and every datum potentially observable by a third party. A pure local model limits reach and availability. The hybrid keeps sensitive work near the operator's physical perimeter while using the cloud for what it is good at: durable, reachable, parallel capacity.

04

THE NEW HUMAN JOB

Human 2.0 is less about typing faster and more about operating well. The core skills become framing outcomes, assigning ownership, setting limits, resolving ambiguity and judging evidence. The person moves up one level, from doing every step to designing and supervising the flow.

This does not remove craft. It concentrates craft where it matters: the definition of done, the quality bar, the decision under uncertainty and the final responsibility to other people. Agents increase surface area. Human judgment keeps that surface area coherent.

The skeptical view is that this is just a speedup — that six agents are six fingers on the same hand. That is wrong. The gain is not only parallelism. It is the separation of concerns: each agent owns a lane, records state independently and returns evidence rather than requiring the human to hold the thread. The human stops being the integration layer and starts being the architect and auditor.

05

OPERATIONS, NOT THEATER

A multi-agent lab only matters if it is dependable. That requires named roles, clear handoffs, current-state checks, private networking, visible failure modes and an audit trail of what changed. A polished response is not proof of work. Reliable operation means the user does not have to discover a silent miss or clean up a plausible mistake.

The lab's physical details reinforce this discipline. One switch defines the wired core. One router defines local access. One HDMI selector makes three mini PCs inspectable through one monitor. Tailscale provides remote reach without opening management ports to the public internet. The design is deliberately countable and testable.

This is also where the "six agents" number stops being arbitrary. A countable, named fleet is auditable. An unnamed swarm is not. If you cannot say how many agents you have, what they are doing and where they run, you do not have a system. You have a vibe. The lab is built to be countable.

06

THE COMPOUNDING ADVANTAGE

The immediate gain is parallelism: six agents can hold more active lanes than one person working serially. The deeper gain is continuity. When agents retain operating context, recurring work becomes easier to restart, monitor and improve. A useful decision made once can inform the next job instead of disappearing into a forgotten tab.

Over time the human gains a personal institution: a small, directed network that remembers standards, watches for change and turns intent into finished artifacts. This is the economic logic of Human 2.0. Capability is no longer limited to hours at the keyboard. It compounds through systems, memory and delegated execution.

The long-term question is not whether one person can do more. It is what becomes possible when one person can sustain a small organization's worth of active, supervised processes — and remains the accountable mind at the center of them. Harari's shared fictions built civilizations. The next step is smaller: a shared operating context built around one person and the network that carries their intent.

—

OBJECTIONS HANDLED

Isn't this just using more software? The distinction is execution, not interface. An app waits for a human to drive it. An agent owns an outcome, runs in its own environment and returns evidence. The human stopped being the app operator and became the system operator.

Why not just use one big agent? A single general agent that does everything inherits every problem: context confusion, accountability diffusion and no principled boundary between local and remote work. A named fleet with explicit roles is auditable. A general agent pretending to do everything is not.

Is this production-ready or a science project? The lab is operational. The physical hardware exists, the network topology is real, Tailscale is in place and the cloud agents are running. This is not a diagram of something planned. It is a report on something running.

What is the cost? Four physical computers on one LAN, two cloud machines with independent providers, one Tailscale account. The point is that the architecture is accessible now, not theoretical. The cost of the hardware is secondary to the cost of the discipline: naming, boundary-setting and verification.

What problem does this actually solve? It solves the bottleneck of one human being the integration layer for every task. The throughput gain is real but secondary. The primary gain is that the human stops being the serial executor and becomes the parallel supervisor — with accountability intact.

PART II — FIELD NOTES

WHAT ACTUALLY HAPPENED

The concepts are the syllabus. These are the days.

The chapters in Part I are reference. The chapters in Part II are report. They are written from a specific desk, with specific machines, during a specific season of unemployment, job applications, and shipping code that had to stay up. The names are real. The failures are real. The point is that the operating model in Part I is not a thought experiment. It is a record.

CHAPTER 01

I DON'T CODE ANYMORE. I VIBE.

Coding used to mean typing. Now it means directing. The difference between prompting for demos and prompting for things that have to stay up.

01

WHAT VIBE CODING ACTUALLY LOOKS LIKE

There is a hype version of vibe coding and a real one. The hype version is "I said one sentence and a whole app appeared." The real version is more like conducting. You set the direction. You correct the drift. You catch the places where the agent optimized for something you did not ask for. You do less typing than you used to, but you do more reading, more judging, and more deciding what to reject.

The day-to-day is not impressive to watch. It looks like a person staring at a screen, reading diffs, asking for changes, accepting some, rejecting others, and slowly steering a piece of software toward a standard it can survive in the wild. The speed is real. The supervision is realer.

"SHIPPED FAST" STOPPED BEING A MOAT

For years, the impressive thing was how fast one person could produce something that worked. That stopped being impressive the moment the model could produce something that worked in minutes. Fast is the baseline now. The new scarce resource is judgment: knowing what to build, what to cut, what to leave out, and what to go back and fix after the demo passes.

A demo that runs once in a conversation is not a product. A thing that survives deployment, edge cases, and a user who does something the agent never anticipated is a product. The gap between those two things is where the work moved.

PROMPTING FOR DEMOS VS. PROMPTING FOR STABILITY

Prompting for a demo is easy. The model has seen every demo pattern in its training data. It knows the happy path. It can produce something visually correct in a few shots. Prompting for something that has to stay up, handle abuse, deal with missing data, survive a deployment at 2 a.m., and not leak credentials — that is a different conversation.

The difference is that stability requires decisions the model is not naturally motivated to make. It will not volunteer to add the error handling, the input validation, the rate limit, the audit log, or the thing that makes the system boring in the way that makes it safe. You have to ask for those things explicitly, and you have to review whether they landed.

WHY YOU STILL HAVE TO KNOW ENOUGH TO CATCH THE LIE

The hardest part of vibe coding is not the prompting. It is the reviewing. The agent will sometimes sound confident about something that is wrong. It will generate code that looks right and fails in a way that is easy to miss if you are not paying attention. The more you rely on the agent, the more important it becomes that you can catch the moment it is lying to you.

This is not about having the model do less. It is about having the human do a different job. The human is the auditor, the taste-maker, the person who says "this looks right but it is not" and then proves it. If you cannot do that, you are not vibe coding. You are trusting.

—

WHY THIS MATTERS IN 2026

"Vibe coding" is a real shift in what the human does, but it is not a replacement for competence. The person who can only prompt and not review will ship garbage faster than ever. The person who can prompt and review will ship better things faster than ever. The difference is not the tool. The difference is the human's ability to tell the difference between a good result and a convincing result.

CHAPTER 02

THE SMALL FACTORY UNDER THE DESK

You don't need a data center. You need a few cheap machines and a standard.

02

THE MACHINES ARE CHEAP NOW

The hardware story of the last few years is that capable small computers are cheap and available. Mini PCs, used office hardware, machines that are more than sufficient to run agents, host services, and keep local work moving — all of it is accessible at a price that does not require a budget review. The barrier is not money. The barrier is knowing what to buy, how to connect it, and how to keep it running when you are not there.

A small factory does not need a data center. It needs a standard. Three or four always-on machines on a LAN. One machine that can do the heavier work when it needs GPU. A network that lets them talk to each other and to the cloud agents without exposing anything to the public internet. The cost is the cost of a few computers and the discipline to keep them named, monitored, and repairable.

OPENROUTER AS THE MODEL LAYER

One of the practical decisions that makes a small operator durable is not marrying a single model provider. OpenRouter and similar abstraction layers let you route work to different models without rewriting the whole system every time a new model appears or a price changes. The agent architecture should be built around the idea that the model is a component you can swap, not an institution you belong to.

This is not about optimizing every prompt for the cheapest model. It is about not being trapped. When the model layer is replaceable, the rest of the system — the workflows, the memory, the verification steps, the review standards — becomes the valuable part. That is the part you keep.

HOW THE SWARM DIVIDES WORK

A swarm is not a single agent that does everything. It is a set of agents with different jobs. In a working setup, the division looks something like this: one agent does research — reading, searching, summarizing, finding the thing that needs to be done. One agent drafts — turning the research into a plan, a spec, or a first cut. One agent builds — implementing the plan in code or in a deliverable. One agent tests — checking that what was built actually works and meets the standard. One agent executes — running the thing in the environment where it has to live.

The division matters because each lane has a different failure mode. Research can hallucinate sources. Drafts can be plausible but wrong. Builds can pass the wrong tests. Execution can fail silently. When everything runs through one agent, all those failures arrive in the same output and have to be caught by the same reviewer. When the lanes are separate, the failures are separate, and the reviewing is easier.

SMALL AND RELIABLE BEATS BIG AND THEATRICAL

The tempting story is to build the biggest, smartest, most general system and let it do everything. The practical story is to build a small system that does a few things reliably, and then add lanes as the work demands them. The small system is easier to understand, easier to audit, easier to fix when it breaks, and easier to trust because you can actually see what it is doing.

Theatrical systems make good screenshots. Reliable systems make good days. The book is about the second kind.

—

WHY THIS MATTERS IN 2026

The hardware is cheap enough that a single person can run a real multi-agent setup without enterprise infrastructure. The constraint is not the machines. The constraint is the operating discipline: naming the agents, defining their lanes, verifying their output, and keeping the whole thing accountable to one human. That discipline is the book's subject.

CHAPTER 03

CLAUDE DREAMS. CODEX SHIPS.

Different models are good at different jobs. Stop using one for everything.

03

THE DREAMER AND THE IMPLEMENTER

Some models are better at generating ideas, explaining strategy, writing the thing that describes what should be built. Others are better at producing the implementation — the code, the structured output, the deliverable that has to actually run. The mistake is using one model for both jobs because it is convenient.

The dreamer role is about breadth, framing, and explanation. The implementer role is about precision, structure, and correctness under constraints. A model that is excellent at one is not necessarily excellent at the other, and the workflow improves when you assign the work to the model that is actually good at that lane.

"WHICH MODEL IS SMARTEST" IS THE WRONG QUESTION

The question that wastes time is "which model is the smartest." The useful question is "which model is the right tool for this lane, at this cost, with this review standard." A model that is slightly less capable overall but dramatically better at the specific work you are delegating is the better choice for that work.

The swarm works because it treats models as specialists, not as a single genius you consult for everything. The human's job is to know which specialist to call for which job, and to review the output when it comes back.

HOW YOU ACTUALLY SWITCH BETWEEN THEM

In a real workflow, the switching is not dramatic. It is practical. You start with the dreamer to frame the problem and produce a spec. You take the spec to the implementer to produce the code or the deliverable. You use a third pass — sometimes the same model, sometimes a different one — to review the result against the spec. The switching happens at the lane boundaries, not in the middle of a sentence.

The discipline is to make the lane boundaries explicit. When the work moves from dream to build, the spec should be in a form the implementer can use. When the work moves from build to review, the standard should be in a form the reviewer can apply. The switching is only smooth when the handoff is clean.

—

WHY THIS MATTERS IN 2026

The model landscape is not converging on one winner. It is diversifying into specialists. The operators who win are the ones who stop asking which model is best and start asking which model is right for which lane. The swarm is not a single model with a bigger context window. It is a small set of specialists with a human who knows how to route work between them.

CHAPTER 04

MUSE, INSTINCT, AND THE REMOTE AGENT WARS

The interesting fight isn't vendor vs. vendor. It's which agent actually lives in your life.

04

WHICH AGENT LIVES IN YOUR LIFE

The loudest conversations are about model capability, benchmark scores, and vendor rivalries. The conversation that matters to an operator is simpler: which agent do you actually use, day after day, for the things that matter to your life and work? A model can be impressive on a benchmark and useless in your workflow if it does not fit the way you work.

The agent that wins is the one you trust with a real task, the one you come back to, the one whose failures you understand and can work around. That is not decided by a benchmark. It is decided by use.

TEXTING AN AGENT LIKE A FRIEND

When an agent becomes usable, the interaction changes. You stop treating it like a tool you invoke and start treating it like something you talk to. You give it a job in the same form you would give a competent person. You expect it to report back. You expect it to ask for clarification when the job is ambiguous. You expect it to remember the context from the last conversation.

The agents that click are the ones that feel usable in that sense. The ones that stay impressive-but-frictionful are the ones you use once for a demo and then go back to doing the hard way.

SCREENSHOTS DO NOT DECIDE WHICH TOOL WINS

The Twitter wars are about screenshots, benchmarks, and hot takes. The real decision is made in private, over weeks, by a person who is trying to get real work done. The agent that survives that test is the one that is actually good at the work, not the one that generated the best promotional content.

This is why the operator's report matters more than the vendor's pitch. The proof is in the work that got done, the things that shipped, the jobs that were applied for, the repos that were reviewed. The screenshot is marketing. The shipping is evidence.

—

WHY THIS MATTERS IN 2026

The agent market is noisy and full of competing claims. The operator's job is to ignore the noise and find the agents that actually carry work. The decision is empirical. Try them on real jobs. See which one you come back to. That is the one that matters.

CHAPTER 05

AGENTS APPLIED TO MY JOB SEARCH BEFORE I DID

Staying unemployed is getting harder, and that's a feature. What happens when the agents apply before you do.

05

THE JOB SEARCH AS A TEST CASE

Unemployment is the place where the agent model gets stress-tested in a way that is hard to fake. The job search has a clear outcome — you get the job or you do not — and it has real stakes. If the agents can apply, track, follow up, and surface the opportunities that matter, that is evidence that the model works on a real human problem.

The test is not "can the agent write a cover letter." The test is "can the agent run a search process that is better than the one the human would run alone, and can the human trust it enough to let it drive."

WHEN THE CONCEPT IS PROVEN

The concept is proven when the outcome arrives. The agent applies. The human gets the interview. The human gets the offer. At that point, the question changes from "can this work" to "what do I do with a working system." Do you turn it off? Do you keep it running? Do you let it keep hunting for a better fit while you are employed?

The interesting question is the last one. A working agent system does not have to stop when the immediate problem is solved. It can keep watching, keep applying, keep surfacing better options. The human who built the system has to decide whether to use that capability and what it means to have a system that can outwork them in the background.

WHAT THIS DOES TO "LOOKING FOR WORK"

The traditional job search is a serial, solo, exhausting process. You find the listing. You write the application. You send it. You wait. You repeat. An agent-assisted search is a parallel process. Multiple applications can be prepared, tailored, and sent without the human doing every step. The human's job shifts from doing the repetitive work to setting the standard, reviewing the output, and deciding what to send.

This is not about cheating the search. It is about making the search a process a human can actually sustain. The market does not care how you applied. It cares whether you are a good fit. The agent is a tool for getting your fit in front of the right people without burning out in the process.

—

WHY THIS MATTERS IN 2026

The job market is going to be one of the first places where agent-assisted work becomes normal, because the work is repetitive, high-volume, and outcome-measurable. The people who figure out how to use agents well in their search will have an advantage. The people who treat agents as a gimmick will spend more energy on the repetitive parts and less on the parts that actually matter — fit, preparation, and performance in the interview.

CHAPTER 06

SOMEONE HAS TO OWN THE OUTCOME

Agents can run all night. They still don't get to be the boss.

06

THE HUMAN SETS THE STANDARD

The agent can generate output all night. It cannot decide what counts as good enough. That is the human's job. The human sets the standard, reviews the work against it, and accepts or rejects the result. The agent is the worker. The human is the boss. The distinction is not symbolic. It is the thing that keeps the system from producing plausible garbage at scale.

The failure mode of full autonomy is not that the agent does nothing. It is that the agent does the wrong thing confidently and the human never catches it because the human abdicated the review. Autonomy without accountability is not freedom. It is negligence with a better UI.

REVIEW IS THE REAL SKILL

The skill that matters in an agent-operated workflow is review. Reading a diff and understanding whether it is right. Rejecting garbage without spending an hour re-prompting. Keeping taste — the sense of what is good, what is clean, what is worth keeping — when the agent is producing fast and in quantity. The human who can review well is the human who can actually use agents well.

This is not a secondary skill. It is the primary skill. The prompting gets easier over time. The reviewing stays hard, because the reviewing is where the judgment lives.

THE FACTORY ONLY WORKS IF ONE PERSON IS ACCOUNTABLE

A factory with no accountable human is a factory that produces whatever the machines produce, including the failures. A factory with one accountable human is a factory that produces what that human accepts. The accountability is what makes the output trustworthy. It is also what makes the system teachable — when something goes wrong, there is a person who owns the fix.

This is the through-line of the whole book. The agents expand the capacity. The human sets the standard and owns the result. The capacity is useless without the standard.

—

WHY THIS MATTERS IN 2026

The pressure toward full autonomy will keep coming. The answer is not to resist the tools. The answer is to resist the idea that the tools replace the human's responsibility. They do not. They amplify it. The human who understands that gets the advantage. The human who does not gets the mistake.

CHAPTER 07

VIBE-CODED APPS GET HACKED. THAT'S THE PRODUCT.

Shipping fast is easy. Shipping something that doesn't leak credentials is the actual work.

07

THE SECURITY PROFILE OF FAST-SHIPPED CODE

Vibe-coded apps have a predictable security profile. They are often sloppy about credentials, about authentication, about dependencies, about input validation, about the things that do not show up in the happy-path demo. The speed of generation makes it easy to produce a lot of code quickly, and the speed of generation makes it easy to miss the boring security details that matter when the app is exposed to the world.

This is not an argument against vibe coding. It is an argument for treating security as part of the loop, not as an afterthought. The app that ships fast and leaks a key is not a success. It is a failure with a faster timeline.

CERBERUS: REVIEW THE REPO, TALK TO THE FINDINGS, PATCH, OPEN A REAL PR

The security review in an agent workflow is not a PDF. It is a conversation. You run the review tool — Cerberus, in the lab's case — against the repo. The tool produces findings. You talk to the findings with the agent. You decide which ones matter. You patch the ones that do. You open a real PR that documents what changed and why. The review is a step in the workflow, not a separate audit that happens after the work is "done."

This is the new loop: generate, review, fix, merge. The security review is one of the review steps. It is not special. It is just the step where you check for the things that would make the app dangerous instead of just incomplete.

SECURITY AS A CONVERSATION WITH THE AGENT

The old model of security review was a gate at the end — a person in a different department goes through the code and writes a report. The new model is a conversation that happens during the build. The agent that wrote the code is the agent that patches it. The human reviews the findings and the patches and decides what to merge. The loop is tight, and the feedback is immediate.

This is better than the old model for one reason: the person who writes the code is the same context as the person who fixes it. The security review is not a handoff to a different team. It is a step the same agent-and-human pair runs before the work leaves the desk.

—

WHY THIS MATTERS IN 2026

The volume of agent-written code is going up. The security review has to keep up. The way to keep up is not to slower the build. It is to make the security review a standard step in the loop, run by the same agents that wrote the code, reviewed by the same human that owns the outcome. The apps that survive are the ones where security is part of the workflow, not a scramble after a leak.

CHAPTER 08

MY OFFICE IS A DESK, POWER, WI-FI, AND A SWARM

Traveling between Chicago and St. Louis killed the idea that work needs a building.

08

WORK DOES NOT NEED A BUILDING

The commute between Chicago and St. Louis makes the point directly. The work does not happen in the building. It happens on the machines, in the workflows, in the agents that keep running when you are not there. The desk is where you sit. The work is distributed across the fleet. The location is almost incidental.

This is not a remote-work argument. It is a distributed-work argument. The human can be in a coworking space, at home, at a desk in a different city, and the work continues because the work is not tied to the human's location. It is tied to the machines and the network and the standards.

TAILSCALE AS THE BORING GLUE

The reason the remote agents are usable is not that they are impressive. It is that the network connects them securely and boringly. Tailscale is the glue. It gives the machines a private network they can use regardless of where they are physically. It does not expose management ports. It does not require a VPN that breaks when you change locations. It just works, and that is the point.

The infrastructure that matters is the infrastructure you do not have to think about. Tailscale is in that category. When the network is boring, the work is not interrupted by the network.

INFRASTRUCTURE OVER AESTHETICS

The workstation setup is not about looking good on camera. It is about running reliably. The mini PCs, the switch, the display plane, the shared monitor, the LAN — all of it is chosen for function, not presentation. The system is inspectable because it has to be. The work is real because it has to survive the human walking away from the desk.

This is the aesthetic of the small factory. It is not beautiful in the way a clean desk photo is beautiful. It is beautiful in the way a working machine is beautiful — because it does the thing it was built to do, consistently, without drama.

WHAT "GOING TO WORK" MEANS WHEN THE TEAM IS SOFTWARE

When the team is software, going to work does not mean commuting to a building. It means connecting to the network, opening the control surface, and checking what the agents did while you were gone. The day starts with a review of the night's work, not with a commute. The human arrives at the work, not at a place.

This is the practical form of Human 2.0. The human is not less present. The human is present in a different way — as the supervisor, the reviewer, the person who sets the standard and signs off on the day's output.

—

WHY THIS MATTERS IN 2026

The geography of work is changing. The people who cling to the office-as-place model will pay for the machinery of commuting and presence. The people who treat the office as a set of machines, a network, and a standard will be able to work from wherever the desk and the power and the Wi-Fi are. The small factory travels.

BUILD IN PUBLIC OR IT DIDN'T HAPPEN

If you can't show the repo, the dashboard, or the broken version, you're just talking.

09

THE WORK HAS TO EXIST BEFORE YOU CAN TALK ABOUT IT

The argument for building in public is not about clout. It is about forcing the work to exist. If you cannot show the repo, you probably do not have the repo. If you cannot show the dashboard, the dashboard probably does not exist. If you cannot show the broken version, you probably skipped the part where the work was actually hard.

Building in public is a discipline. It is the commitment to make the work visible at every stage, including the stages where it is ugly and incomplete. That commitment is what separates the people who ship from the people who talk about shipping.

CHAPTER 10

THE FIRST-TRY PROBLEM

We have agents that can apply to jobs and review repos. We still sit there regenerating answers.

10

THE UX PROBLEM THAT HAS NOT BEEN SOLVED

The current LLM experience still feels, in important ways, like fighting the tool. You prompt. You get an answer. The answer is almost right. You tweak the prompt. You get a new answer. You repeat. The friction is not always in the model's capability. It is in the interaction — the need to regenerate, to re-prompt, to nudge the model back onto the path you wanted.

This is the first-try problem. The tool should get it on the first try more often than it does. When it does not, the user pays the cost in time, attention, and patience. The cost is small in a one-off chat. The cost is large when the agent is running in a loop and every misstep requires a human correction.

PROMPT TWEAKING AS WASTED MOTION

Prompt tweaking is the visible form of the first-try problem. The user spends time adjusting the prompt instead of spending time on the work the prompt was supposed to enable. The tweaking is not always wasted — sometimes the refinement is the work — but often it is just the cost of a tool that has not yet learned to get it right the first time.

The measure of a good agent system is not whether it can be prompted to do the thing. It is whether it can do the thing with a prompt that is close to the first one you would naturally write. The gap between those two things is the UX gap that still needs to close.

WHY THIS MATTERS MORE IN LOOPS

In a one-off chat, the first-try problem is an annoyance. In a loop — an agent that runs, checks, retries, and reports — the first-try problem is a throughput problem. Every time the agent does not get it on the first try, the human has to intervene, or the agent has to retry, or the workflow has to absorb the cost of the miss. The loop amplifies the cost of every miss.

This is why the first-try problem is not a minor UX issue. It is one of the things that determines whether an agent system is actually useful in sustained operation or only impressive in a demo. The demo hides the misses. The loop exposes them.

WHAT "JUST GETS IT ON THE FIRST TRY" REQUIRES

The first-try standard requires better models, better prompts, better context, and better standards for what "right" means. It requires the agent to understand the intent well enough to produce a usable result without a conversation. It requires the human to be able to trust the first result enough to not need to double-check every step. It requires the system to be reliable enough that the first try is usually enough.

This is the hard problem. The agents can do a lot. They do not yet get it on the first try often enough. Closing that gap is one of the things that will determine how useful the agent age actually is.

—

WHY THIS MATTERS IN 2026

The first-try problem is the gap between the demo and the daily use. The demo is one prompt, one result, one wow. The daily use is many prompts, many results, many corrections, and a human who has to decide whether the tool is saving time or costing it. The tools that close the first-try gap will be the ones that move from impressive to indispensable.
